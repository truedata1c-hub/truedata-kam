# PharmaCheck · Переговоры — ТЗ v0.2

Модуль управления переговорными кампаниями КАМ с аптечными сетями. Рынок — Россия, контур PharmaCheck (факт исполнения — данные МДЛП). Эталон экранов — `kam-negotiations-prototype-russia`; эталон архитектуры, оформления и порядка разработки — серверная MDM (`truedata1c-hub/truedata-mdm`). Репозиторий модуля — `truedata1c-hub/truedata-kam`.

v0.2 заменяет v0.1: добавлены ответы Сергея по функционалу от 17.11.2026 (разбивка по брендам и кварталам, конструктор ролей и цепочек, прошлый период и обоснование, аналитика, канал писем).

## 1. Решения Сергея от 17.11.2026

1. Модуль для России, бренд TrueData / PharmaCheck, валюта RUB, юрлица по ИНН.
2. Живёт там же, где MDM: московский VPS, Docker Compose за существующим Traefik, адрес `kam.demo.truedata.tech`.
3. Оформление полностью повторяет MDM (оболочка PharmaView / TrueData Demo Shell).
4. Делаем рабочую систему, а не прототип: на стенде демонстрационные данные и пользователи.
5. Для заказчика переговоры — раздел PharmaCheck; модуль встраивается в страницу платформы со сквозным входом (§2.1, §2.2). Собственный вход модуля — для демо и администрирования; с MDM вход не общий.
6. Этапы кампании — шесть (§4).
7. Кампания ведётся по сети и охватывает выбранные юрлица сети (ИНН) — так же, как PharmaCheck отслеживает исполнение по спискам ИНН сети.
8. У сети может быть несколько кампаний одновременно: годовые условия и параллельно разовые акции.
9. Версия предложения содержит инвестиции и ожидаемый оборот с разбивкой **по брендам и кварталам**; ROI рассчитывается обязательно (§6).
10. Инвестиции — все выплаты сети по условиям кампании; отдельной строки BTL нет.
11. Роли и цепочки согласования собираются в конструкторе: администратор заводит роли (руководитель КАМ, финансовый директор, финансовый контролёр и любые другие) и выстраивает их в маршруты (§3, §5).
12. Решения согласующего — только «Согласовать» и «Отклонить»; «согласовать с условием» не делаем.
13. Нужны переписка внутри кампании и контрольная дата.
14. Уведомления на демо — внутри системы; канал писем заложен в систему сразу и включается подключением почтового сервера (§8.1).
15. Обязательно сравнение с прошлым периодом: план и факт прошлого периода по сети, бренду и кварталу; КАМ обосновывает план текущего периода (§6.2).
16. Нужны аналитические блоки по этапам и результатам (§8, экран «Аналитика»).
17. Финальная загрузка согласованных условий в PharmaCheck по шаблону — последний этап, работу не блокирует. В модуле на её месте хранение финального файла.
18. Документы любых форматов хранятся как есть и не разбираются в условия.
19. Суммы показываются как «сумма, ₽» без признака НДС; правило учёта НДС не задаётся.
20. Демо: российские сети и КАМы из прототипа, около 80 кампаний на разных этапах, 2–3 шаблона маршрутов.

## 2. Размещение и технологии

Отдельный сервис по образцу MDM. Общее с MDM переиспользуется копированием проверенных частей.

| Часть | Выбор | Откуда берём |
| --- | --- | --- |
| API | Node.js 22 + TypeScript, Fastify, префикс `/api/kam/v1` | каркас `src/app.ts`, `errors.ts`, `commands.ts` MDM |
| Хранилище | PostgreSQL 16, схема `kam`, SQL-миграции | порядок `migrations/` MDM |
| Файлы | каталог на диске данных вне веб-корня, SHA-256 в БД | `upload.ts` MDM |
| Фоновые задания | отдельный процесс, очередь в PostgreSQL | `jobs.ts` MDM: уведомления, письма, сроки |
| Интерфейс | Vue 3 + Quasar, отдаётся тем же сервисом | `theme.css`, оболочка `App.vue`, `Icon.vue`, `TdSelect.vue`, `icons.svg`, логотип, Inter |
| Вход | сквозной из платформы + собственные учётные записи | `auth.ts` MDM |
| Развёртывание | Compose project `truedata-kam`: `api`, `worker`, `db`; сеть `coolify` | `deploy/` MDM |
| Выпуск | GitHub Actions: тесты на каждом коммите, выпуск по тегу | `.github/workflows/` MDM |

Договорённости API как в MDM: ревизия `If-Match`, `Idempotency-Key` для команд, ответы 403 / 404 / 409 / 422 с кодом ошибки, все клиентские ключи содержат `client_id`, неизменяемый журнал событий в той же транзакции, что и изменение.

### 2.1. Место в меню платформы

- В основной системе разработчики добавляют пункт «Переговоры» в блок PharmaCheck. По клику модуль загружается на той же странице, внутри оболочки платформы.
- **Встроенный режим**: без собственного меню и шапки. Высоту, заголовок для хлебных крошек и переходы модуль сообщает платформе через `postMessage`.
- **Самостоятельный режим** (прямой адрес): собственное меню, повторяющее блок PharmaCheck — «Дашборды → Переговоры → Договоры → Базовые отчеты → Мои отчеты → Общие отчеты»; активны «Переговоры», остальные на демо неактивны.

### 2.2. Сквозной вход

1. По клику на «Переговоры» сервер платформы выпускает одноразовый подписанный токен на 60 секунд: пользователь, email, имя, компания, `jti`. Подпись асимметричная (EdDSA или RS256); модуль хранит открытый ключ платформы.
2. Встроенная страница открывает `/sso?token=…`.
3. Модуль проверяет подпись, срок, издателя, адресата и неиспользованность `jti`, создаёт сессию (cookie `HttpOnly`, `Secure`, `SameSite=Lax`, до 12 часов).
4. При первом входе пользователь создаётся автоматически; роли и область видимости назначает администратор модуля.
5. Модуль и платформа на одном домене второго уровня (`*.truedata.tech`); встраивание разрешено только адресам платформы (`Content-Security-Policy: frame-ancestors`, список — настройка).

От разработчиков платформы: пункт меню и страница со встроенным окном, выпуск токена по клику, открытый ключ. Если платформа уже выпускает JWT (например, для Hasura), используется тот же механизм. Для проверки до подключения модуль содержит тестовый «запускатель», выпускающий такие же токены от имени демо-платформы.

## 3. Роли, оргструктура и видимость

### 3.1. Конструктор ролей

Администратор заводит **бизнес-роли** клиента: КАМ, руководитель КАМ, национальный руководитель, финансовый директор, финансовый контролёр, коммерческий директор, бренд-менеджер и любые другие. Роль = набор полномочий + область видимости.

Полномочия (системный перечень, отмечаются галочками):

| Полномочие | Смысл |
| --- | --- |
| Вести кампании | создавать, менять, загружать документы и версии, отправлять на согласование |
| Вести кампании подчинённых | то же за сотрудников ниже по оргструктуре |
| Согласовывать | быть исполнителем шага маршрута |
| Смотреть аналитику | экран «Аналитика» в своей области видимости |
| Администрировать | пользователи, роли, оргструктура, сети, бренды, маршруты, типы кампаний, настройки |

Область видимости роли: свои сети / сети подчинённых / все сети клиента / выбранные бренды (для бренд-менеджеров: видят строки своих брендов во всех кампаниях, суммы чужих брендов — только итогом).

Пользователь может иметь несколько ролей. Демо поставляется с готовым набором ролей, администратор меняет их без разработки.

### 3.2. Оргструктура

- У пользователя указывается руководитель; цепочка любой глубины. Изменение руководителя действует с даты.
- Закрепление КАМ за сетями — с периодом действия. Сеть может быть закреплена за несколькими КАМ.
- Замещение: пользователь или администратор назначает заместителя на даты.

### 3.3. Общие правила

- Пользователь одного клиента получает 404 на данные другого.
- Самосогласование запрещено: автор отправки не может быть исполнителем шага (§5).

## 4. Кампания и этапы

**Кампания** — переговоры с одной аптечной сетью об условиях на период:

- сеть и **юрлица сети (ИНН)**, на которые распространятся условия: по умолчанию все действующие юрлица сети, КАМ может снять лишние;
- тип: годовые условия, пересмотр, ассортимент, разовая акция (список и правила ведёт администратор);
- название, период действия будущих условий (произвольные даты), **контрольная дата** — к ней условия должны быть согласованы (по умолчанию за 14 дней до начала периода);
- ответственный КАМ, валюта RUB.

У одной сети может быть несколько кампаний одновременно. При пересечении периодов кампаний одного типа система предупреждает, но не запрещает.

| № | Этап | Вход | Кто переводит |
| --- | --- | --- | --- |
| 1 | Подготовка | создание кампании | КАМ |
| 2 | Переговоры с сетью | КАМ начал работу с сетью | КАМ |
| 3 | Внутреннее согласование | отправка текущей версии; заполнены разбивка и обоснование | КАМ |
| 4 | Согласовано внутри | все обязательные шаги маршрута согласовали | система |
| 5 | Подтверждено сетью | КАМ отмечает согласие сети и прикладывает документ-подтверждение | КАМ |
| 6 | Финальные условия | загружен финальный файл условий; выгрузка в PharmaCheck — этап 2 | КАМ |

Исходы: **Отменена** (с причиной, из этапов 1–5) и **Закрыта** (после этапа 6).

- Отклонение на любом шаге возвращает кампанию на этап 2 с обязательным комментарием. Повторная отправка — только с новой версией.
- КАМ может отозвать отправку до первого решения.
- Новая версия после этапа 4: если итог инвестиций не вырос и итог оборота не снизился, этап 4 сохраняется, согласующим уходит уведомление; иначе — возврат на этап 2. Допуски задаются в шаблоне маршрута.
- Просроченная контрольная дата подсвечивается в портфеле и аналитике и рассылает уведомление КАМ и руководителю.

## 5. Маршруты согласования

Администратор ведёт **шаблоны маршрутов** — упорядоченные цепочки шагов, собираемые в конструкторе.

Шаг шаблона:

- исполнитель — один из вариантов:
  - **руководитель автора** (по оргструктуре на дату отправки);
  - **руководитель уровня N** (руководитель руководителя и выше);
  - **бизнес-роль** («любой пользователь с ролью „Финансовый директор“», с уточнением по области видимости);
  - **конкретный пользователь**;
- условие включения (шаг пропускается, если ложно): итог инвестиций ≥ порога; рост инвестиций к факту прошлого периода ≥ X %; ROI ниже факта прошлого периода; тип кампании; сеть или группа сетей; бренд в разбивке;
- срок решения в рабочих днях, напоминание и уведомление руководителю при просрочке;
- допуски для повторной версии (§4).

Выбор шаблона: правила по типу кампании и группе сетей с приоритетом; шаблон по умолчанию обязателен. В конструкторе есть **предпросмотр**: выбрать любую кампанию и увидеть, какие шаги и какие люди получатся.

- При отправке маршрут **замораживается** в кампании с вычисленными исполнителями.
- Решения: «Согласовать» (комментарий по желанию), «Отклонить» (комментарий обязателен).
- Автор отправки и ответственный КАМ не могут быть исполнителями. Если исполнитель шага — один из них, шаг переходит к руководителю следующего уровня (по цепочке автора); если такого нет, отправка отклоняется с объяснением. Роль без полномочия «Согласовывать» или без активных пользователей в шаг не ставится.
- Условия «рост к факту прошлого периода» и «ROI ниже прошлого» без данных прошлого периода считаются выполненными: шаг включается.
- Заместитель на даты решает активные шаги замещаемого; в истории — «решил Б за А».
- Параллельные шаги в первую версию не входят; модель хранит режим шага.

Демо-шаблоны: «Годовые условия» (руководитель КАМ → национальный руководитель → финансовый директор при инвестициях ≥ 10 млн ₽), «Разовая акция» (руководитель КАМ → финансовый контролёр при инвестициях ≥ 250 тыс. ₽ — порог снижен под масштаб демо-акций), «По умолчанию» (руководитель КАМ).

## 6. Документы, версии и разбивка

### 6.1. Документы

- Любой формат, до 50 МБ (настройка); исполняемые файлы запрещены.
- Тип: наше предложение, встречное предложение сети, протокол встречи, расчёт, подтверждение сети, подписанный договор, финальные условия, прочее.
- Хранится неизменяемо: имя, размер, тип файла, SHA-256, автор, время, этап, комментарий. Удаление — архив с причиной.
- Просмотр в браузере: PDF и изображения; остальное — скачивание.
- Документы не разбираются в условия. Извлечение текста и поиск — этап 2; подсказки ИИ — этап 3 с согласия клиента.

### 6.2. Версия предложения

**Версия** — то, что согласуется; номер автоматически (v1, v2, …); после создания неизменяема.

Состав:

- **Разбивка**: строки — бренды, столбцы — периоды кампании (по умолчанию кварталы; деление задаёт тип кампании: месяц, квартал, четыре месяца, весь период). В каждой ячейке — **инвестиции, ₽** и **ожидаемый оборот, ₽**.
- Итоги по брендам, периодам и кампании считаются системой.
- **ROI = ожидаемый оборот / инвестиции** — по ячейке, бренду, периоду и кампании. Подсказка в интерфейсе: «Оборот на 1 ₽ инвестиций; не окупаемость».
- **Обоснование** — обязательный текст версии при отправке на согласование: почему такие условия и как они соотносятся с прошлыми результатами. Комментарий по бренду — по желанию.
- Ссылки на документы кампании, на которых основана версия.

Ввод разбивки:

- таблица в интерфейсе с вставкой из буфера обмена (копирование блока ячеек из Excel);
- скачивание шаблона Excel с брендами и периодами кампании и загрузка заполненного обратно. Это собственный шаблон модуля со строгой структурой — не разбор произвольных документов.

Сравнение версий: дельта по ячейкам, брендам и итогам к предыдущей и к согласованной версии.

### 6.3. Прошлый период

- Для сети хранятся **план и факт прошлых периодов** по бренду и кварталу (инвестиции, оборот) и ROI.
- Источник на этапе 1 — загрузка администратором из Excel по шаблону модуля (на демо — демонстрационные данные); этап 2 — автоматически из PharmaCheck по ИНН сети.
- В карточке кампании и в версии рядом с планом показываются план и факт сопоставимого прошлого периода, отклонения и выполнение плана прошлого периода.
- **Подсветка для обоснования**: рост инвестиций по бренду выше порога, ROI ниже факта прошлого периода, бренд без факта прошлого периода, невыполнение плана прошлого периода. Пороги — настройка. Подсветка не блокирует отправку, но видна согласующим.

## 7. Работа с сетью

- **Контакты** привязаны к сети: имя, роль в сети, ключевой. Удаление — архив.
- **Активности**: дата, формат (встреча, звонок, письмо), контакт, статус (запланирована / завершена), цель или итог. Завершённые попадают в «пульс переговоров».
- **Переписка кампании**: лента комментариев участников (КАМ, руководители, согласующие), упоминание пользователя через @ с уведомлением. Отдельно от решений по маршруту.

## 8. Экраны

Оформление — как MDM: меню 220 px со сворачиванием до 56 px, Inter 12/18, цвета `#101828 / #344054 / #667085`, границы `#eaecf0`, фиолетовый `#6941c6` только для основных действий, серые контурные иконки, контролы 30 px, белые карточки с радиусом 8–9 px, графики ApexCharts.

1. **Портфель кампаний.** KPI в контексте роли (активные, ждут решения, согласовано, просрочены по контрольной дате, инвестиции, оборот, ROI); фильтры: год, этап, тип, сеть, бренд, КАМ, поиск; таблица; чип этапа открывает «пульс переговоров».
2. **Карточка кампании.** Шапка с метаданными, юрлицами и действиями; строка этапов; KPI версии; разбивка бренд × период с прошлым периодом; обоснование и подсветки; версии и сравнение; документы; панель согласования; история решений; переписка; контакты и активности.
3. **Мои решения.** Очередь шагов со сроками и просрочкой.
4. **Аналитика.**
   - воронка этапов: количество кампаний и суммы на каждом этапе;
   - время: средняя длительность этапов и согласования, просроченные шаги и контрольные даты;
   - инвестиции, оборот, ROI по брендам, сетям, кварталам, КАМ;
   - план текущего периода против плана и факта прошлого периода;
   - доля согласованного объёма к плану года;
   - всё в области видимости пользователя (бренд-менеджер видит свои бренды).
5. **Сети** (администратор). Сети, юрлица с ИНН, регионы, группы сетей, закрепление КАМ, загрузка прошлых периодов.
6. **Бренды** (администратор). Справочник брендов клиента; позже — из домена «Препараты» MDM.
7. **Маршруты согласования** (администратор). Конструктор шаблонов, правила выбора, предпросмотр.
8. **Пользователи, роли и оргструктура** (администратор). Конструктор ролей, руководители, замещения.
9. **Настройки** (администратор). Типы кампаний и деление периодов, пороги подсветок, почтовый канал.
10. **Журнал изменений.**

### 8.1. Уведомления

- Каталог событий: новый шаг согласования, решение, возврат на доработку, напоминание и просрочка шага, просрочка контрольной даты, упоминание в переписке, подтверждение сетью.
- Каналы: **в системе** (значок и центр уведомлений) — работает сразу; **почта** — заложена: шаблоны писем, очередь отправки, повтор при ошибке, журнал. Включается заполнением настроек SMTP; пока сервер не подключён, письма копятся со статусом «канал не настроен» и не теряются.
- Пользователь выбирает, какие события получать письмом.

## 9. Приёмочные сценарии

1. КАМ видит только закреплённые сети; руководитель — кампании своих подчинённых любой глубины; пользователь другого клиента получает 404.
2. Администратор заводит роль «Финансовый контролёр», включает её в шаблон; при отправке подходящей кампании шаг уходит пользователю с этой ролью.
3. Создание кампании: по умолчанию выбраны все юрлица сети; снятое юрлицо не попадает в кампанию.
4. Две кампании одной сети (годовая и акция) существуют одновременно; пересечение двух годовых даёт предупреждение.
5. Версия с разбивкой 3 бренда × 4 квартала: итоги и ROI совпадают с ручным расчётом; вставка блока из Excel и загрузка шаблона дают ту же версию.
6. Отправка без обоснования или с пустой разбивкой отклоняется с 422.
7. Шаблон «руководитель автора → финансовый директор при инвестициях ≥ 10 млн ₽»: при 6 млн ₽ второй шаг пропущен.
8. Отклонение без комментария невозможно; после отклонения повторная отправка той же версии невозможна.
9. Правка шаблона во время согласования не меняет идущий маршрут.
10. Заместитель на даты отсутствия получает шаг; в журнале видно «решил Б за А».
11. Автор не может согласовать свою кампанию.
12. Новая версия после этапа 4 с ростом инвестиций возвращает кампанию на этап 2.
13. Бренд-менеджер видит в аналитике и кампаниях строки своего бренда, по остальным — только итоги.
14. Подсветка: рост инвестиций бренда выше порога к факту прошлого периода виден в версии и у согласующего.
15. Просрочка шага и контрольной даты создаёт уведомления; без SMTP письма в очереди со статусом «канал не настроен», после настройки отправляются.
16. Сквозной вход: токен демо-платформы открывает модуль во встроенном окне; повтор того же токена отклоняется.
17. Конфликт ревизий (409), идемпотентность команд, перезапуск без потери данных, восстановление из резервной копии.
